# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`rocketjob` is a Ruby gem: a distributed, MongoDB-backed batch processing system. Jobs are Mongoid documents persisted to MongoDB; servers pull queued jobs and run them across worker threads. There is no Rails app here, only the library plus its test suite. The web UI (Mission Control) and Tabular plugins live in separate gems.

The primary public interface is `RocketJob::Job`; capabilities are added by mixing in modules such as `RocketJob::Batch`. Treat that surface (subclassing `Job`, opt-in mixins, typed fields, `#perform`, queuing/downloading, documented state transitions) as the stable contract; everything under `Plugins`, `Sliced`, and the runtime classes is internal.

## Why this design

Context worth knowing before changing core behavior:

- **Two tiers of jobs.** Simple jobs (`RocketJob::Job`) are conventional background jobs like other frameworks offer. Batch jobs (`include RocketJob::Batch`) are the real point of Rocket Job: a single job's input is uploaded into a dynamically created MongoDB collection, split into slices, and processed concurrently across thousands of workers (often Docker containers). Output is written back to MongoDB the same way.
- **Why MongoDB.** Its atomic `find_and_modify` lets thousands of nodes claim work without colliding, and it spills from memory to disk, which is essential for very large files. Rocket Job was built because Sidekiq/Redis could not scale this way (Redis was single-threaded and could not overflow to disk). **AWS DocumentDB is supported with polling**: the `Event`/`Subscriber` pub-sub mechanism (`lib/rocket_job/event.rb`) tails a *tailable capped collection* by default, and DocumentDB still does not support capped collections (verified June 2026 against AWS docs), so on DocumentDB `RocketJob::Event.listener_strategy = :polling` polls a regular collection with a TTL index instead (since v7). `docs/installation.md` ("AWS DocumentDB") documents it and its settings.
- **Why Mongoid.** Jobs are documents with real, typed, validated fields, not an untyped hash of arguments.
- **Backward compatibility is a priority.** Only break it in a major release, ideally with a deprecation path first. Most forced changes come from breaking changes in MongoDB/Mongoid. When adding persisted fields to a plugin, give them defaults so existing jobs in the database still load.

A class diagram of the core relationships, and the architecture overview, is in [docs/architecture.md](docs/architecture.md) (published as `architecture.html`). `CONTRIBUTING.md` only points to it.

## Commands

Tests require a running MongoDB on `127.0.0.1:27017` (see `docker-compose.yml`: `docker compose up -d`). Test config is `test/config/mongoid.yml` and the suite drops/recreates collections on load.

- Run full suite (against current `Gemfile`): `bundle exec rake test`
- Test logs go to `test.log` (not stdout); use it to debug failures.

`rake` with no args runs the full matrix via Appraisal, not a single test run. Don't use bare `rake` for quick iteration.

### Multi-version testing (Appraisal)

CI runs against multiple Mongoid/Rails/Ruby combinations defined in `Appraisals` with generated gemfiles in `gemfiles/`. To target one combination:

- `BUNDLE_GEMFILE=gemfiles/mongoid_9.1.gemfile bundle exec rake test`
- Regenerate gemfiles after editing `Appraisals`: `bundle exec appraisal install`

### Test conventions and gotchas

Useful things learned writing tests:

- **Coverage.** SimpleCov runs automatically (started in `test_helper.rb`). After a run, overall % prints to stdout and `coverage/.resultset.json` holds per-file line hits — parse it to find the least-covered files and exact missing line numbers. `coverage/index.html` is the browsable report.
- **Shared class-level state must be reset between tests.** `Supervisor` keeps `@shutdown`/`@event` (`Concurrent::Event`) as class instance vars; `Event` keeps a class-level `@subscribers` map; `Subscriber` has `@test_mode`. Reset these in `before`/`after` or tests leak into each other. See `test/supervisor_test.rb` / `test/event_test.rb` for the reset helpers.
- **Autoload ordering.** Constants are `autoload`ed in `lib/rocketjob.rb`. Some files trigger circular loads when referenced first in isolation — e.g. referencing `RocketJob::WorkerPool` before `RocketJob::Supervisor` fails because `worker_pool.rb` requires `supervisor/shutdown`. Fix by `require`ing the dependency (e.g. `require "rocket_job/supervisor"`) at the top of the test.
- **Exercising persisted/legacy documents.** `Mongoid::Factory.from_db(JobClass, doc_hash)` instantiates with `new_record? == false` and fires `after_initialize`, as reading a document from the database does, without saving one first (for example a category saved by v7 with `format_options`). The v5→v6 batch category migration was removed in v8. A plain in-memory hash can hold Ruby Symbols that `test_helper.rb` would otherwise reject on BSON serialization.
- **State without the state machine.** `Job.new(state: :completed)` sets the field directly so predicates like `completed?` work without driving an `aasm` transition. Batch sub-states are similar: `job.start; job.sub_state = :processing`.
- **Driving real worker threads.** `ThreadWorker.new` immediately spawns a thread running `#run`; if you `kill` it before it enters `run`, the `Shutdown` exception is unhandled and `join` re-raises it — let the thread start first. A plain `Worker` is the inline/no-op strategy and is trivially testable.
- **ActiveRecord in tests.** `upload_arel`/transaction tests use a sqlite DB via `test/config/database.yml` + an inline `ActiveRecord::Schema.define`. See `test/plugins/transaction_test.rb` and `test/sliced/input_query_test.rb`.
- **Misc.** `DirmonEntry#pattern` is unique-validated (use distinct patterns per fixture). `Batch::Model#worker_count` caches for one second. `Category#file_name` returns an `IOStreams::Path`, not the raw string. Whether a set of job properties (a `DirmonEntry`'s or an `UploadFileJob`'s) can build the job is decided by the job class: `.property_errors` in `Plugins::Job::Model` checks the setters, and `Batch::Categories` overrides it to ask each category, via `Category::Base#property_errors` on a copy of the job's default categories, whether its properties (names and values) can be merged into it. The job is never built, so user `after_initialize` callbacks do not run during validation.
- **`output_category`/`input_category` are Batch-only** (defined in `lib/rocket_job/batch/categories.rb`). A plain `RocketJob::Job` does **not** respond to them, and a simple job has no persisted `result`/output: `perform_now` simply returns the value `#perform` returned (`@rocket_job_output`). To keep a result on a simple job, store it in an explicit `field`. (The pre-2026 `guide.md` examples that called `output_category` on a non-batch job and asserted `{'result' => 45}` were wrong.)

## Architecture

The structure is in `lib/rocket_job/` and [docs/architecture.md](docs/architecture.md). What the code does not explain:

- **Category schemas.** Batch input/output categories (`RocketJob::Category::Input`/`Output`) each have a `schema` (an IOStreams/Frictionless Table Schema: a Hash, or the path or url of a JSON file; it replaced `format_options`, which 7.1 deprecates and v8 removed, as v8 removes each option that 7.1 deprecates: each category class names them (`Category::Base.removed_option_names`), and a category saved with one set to a value that had an effect raises when it reads or writes records (`#check_removed_options`), since Mongoid keeps a removed field among the attributes of a saved document, where it would otherwise be ignored without a word, while one left at a value that had no effect, such as a blank `format_options`, is dropped (`.supported_properties`); it also replaced the column options `allowed_columns`/`required_columns`/`skip_unknown`/`header_cleanser` and an application's `columns`, which v8 removed the same way. An input category's `columns` is still a field, but only v7 set it, to the header row of a file uploaded without a schema; v8 never sets it: an upload without a schema raises while it is set (`#check_columns_not_set`, which also catches the stale header row that v7 copied into the next run of a scheduled job), and a worker raises for columns that change when read back as a header row (`#check_header_row`), so the lines and columns that v7 uploaded still work. `upload` rejects the column options that it took in v7 (`allowed_columns:`, `required_columns:`, `skip_unknown:`, `cleanse_header:`), naming them itself, since IOStreams 3.0 removed them and no longer lists them. `mode` is a removed option too, no longer a field: `validate_rows` replaces `mode: :hash` (and `upload`'s `validate_rows:` replaces `stream_mode:`, which raises), and `:array` has no replacement. A job class, or a new Dirmon entry or `UploadFileJob`, that sets any `mode` other than `:line` raises (so does a value v7 rejected too, such as `:hashes`); `:line` is dropped. A category that v7 saved is converted when it is read (`Category::Input#convert_saved_mode`, an `after_initialize`): `"hash"` becomes `validate_rows: true` in a category with a format, unless `validate_rows` was saved too (it defaults to nil, so that false can be told apart), and `"hash"` without a format and `"line"` are dropped. The conversion is a change (`remove_attribute("mode")` plus the `validate_rows` setter), so the next save of the job `$unset`s `mode`: otherwise a dropped `"hash"` would come back as `validate_rows: true` once a format was set, and a converted one could never be cleared. Mongoid runs an embedded document's `after_initialize` after its `_index` is set (8.1 to 9.1), which `remove_attribute` needs for its `$unset` path. A saved Dirmon entry or `UploadFileJob` converts its properties the same way when it is read (`after_initialize :convert_saved_properties`), asking its job class (`Plugins::Job::Model.convert_saved_properties`), which batch overrides to ask each default category (`Category::Base#convert_saved_properties`), whose format applies when the properties have none. `"array"` is kept, so that `create_restart!` still saves the next run of a v7 scheduled job, and `#check_upload` raises for it, while the Arrays that v7 already uploaded still parse. Batch jobs override `input_categories=`, so a test that simulates a v7 category saves the job, `$set`s the attribute and reloads it. `validate_rows` is not a field named `validate`, since Mongoid rejects a field that overrides `ActiveModel#validate`. Main has no deprecation-warning code (`RocketJob::Deprecation`) or schema proposals (`RocketJob::SchemaProposal`): those live on the `v7` branch, for 7.1).
- **Slices of the rows of a file.** In a tabular format, with or without a schema, IOStreams writes the lines of an uploaded file (`copy_from(path, mode: :line)`), or the lines that the block of `upload` writes (`writer(:line)`), to the input in slices: `Sliced::Writer::Input` is the store of slices (`IOStreams::Slice::Target`), and `Category::Input#copy_slices`/`#write_slices` give the stream the category's schema and format. Each slice holds the header row of its file and its format (`IOStreams::Slice`), so a category never stores a header row, and files with columns in another order can share one category. A slice document stores `IOStreams::Slice#to_h` under `"s"`, without reading its keys, beside `Sliced::Slice::ROWS_GUARD` under `"r"`, where Rocket Job 7 reads records, so a v7 worker fails such a slice instead of processing nothing. Workers parse a slice with `IOStreams.stream(slice).schema(...)` in `Category::Input#parse_records`; a row that cannot be parsed raises before it is yielded, which is why the slice loop points `processing_record_number` at the next record (and leaves it on the last record once that is processed). Assigning a plain Array to `Slice#records` keeps the header row and format of the rows it replaces, unless it holds Hashes. Only a category without a format, or in a format whose rows are not lines of text (`:hash`, `:array`, Parquet; `Category::Input#slices?` asks IOStreams), uploads records one at a time (`Category::Input#each_record`), as they are, since v7 and v8 servers never run together (see `docs/upgrading.md`). Since the slice path does not build the category's `IOStreams::Tabular`, `#slice_target` and `#parse_records` call `check_removed_options` themselves.
- `lib/rocket_job/extensions/` monkey-patches Mongoid/Mongo/Psych. Notably, **BSON Symbols are deliberately unsupported** (Mongoid/MongoDB deprecated them); `test_helper.rb` raises if a Symbol is serialized. Use the `StringifiedSymbol` type / strings for field values.

## Sister projects (checked out alongside this repo)

These related gems live next to `rocketjob` on this machine and are frequently referenced when working on docs or behavior. They are separate repos, not part of this gem.

- **`../rocketjob_mission_control`**: the web UI for Rocket Job (gem `rocketjob_mission_control`). It is a **Rails engine** mounted into any Rails app via `mount RocketJobMissionControl::Engine => "..."` in `routes.rb`. Docs refer to it as "Mission Control"; its screenshots live under `docs/images/rjmc/`.
- **`../semantic_logger`** — the logging gem Rocket Job uses (`SemanticLogger`). Its `docs/index.md` is the explicit style model for Rocket Job's rewritten landing page. Canonical site: `https://logger.reidmorrison.com`. The Rails companion is `rails_semantic_logger`.
- **`../iostreams`** (gem `iostreams`) — powers batch `upload`/`download` streaming and the Zip/GZip/encrypted/delimited/fixed-length file handling.
- **`../symmetric-encryption`** (gem `symmetric-encryption`) — the encryption library behind the `encrypted` category serializer and encrypted fields. `RocketJob::Config.load!` optionally loads `config/symmetric-encryption.yml` (3rd arg, defaults to that path).
